## 3. Поток заказа (as is, после правок 2026-11-01)

1. Пользователь выбирает файл → считается SHA-256 в браузере (`certify_form.js`).
2. `POST /.netlify/functions/order-create` → создаёт заказ, возвращает `order_id`, `hmac_token`, `upload_url`, `upload_headers`.
3. Фронт делает **PUT по `upload_url`** → файл летит в **Supabase Storage** (путь `orders/<orderId>_<fileName>`).
   - ❗ `file_key_r2` в БД **не пишется**.
4. `POST .../functions/v1/process-payment` → списывает токен, ставит `completed`, дёргает `order-process` (fire-and-forget).
5. `order-process` пытается `HeadObject` в R2 по `file_key_r2` → **`file_key_r2 = null`** → `r2_head_failed` → обрыв.
6. Фронт параллельно зовёт `order-confirm` → HMAC проверяется, но статус уже `completed`, а не `pending_upload` → возвращает `idempotent: true`, ничего не делает.
7. Страница статуса показывает `completed`, но `pdf_url = null`, кнопки скачивания нет, письма нет, `tsa/anchor/vt = pending`.

### Итог: где именно ломается
**Рассинхрон хранилищ.** `order-create` кладёт файл в **Supabase Storage**, а `order-process`/`order-confirm` ищут в **R2** по `file_key_r2`, который никогда не заполняется.

### 2026-11-15 (Roadmap: Immutable Audit Trail / Proof of Reserves)
**Контекст:** Чтобы система не была "погремушкой", а представляла собой реальный финтех-инструмент, нам нужна доказуемая система учета. Никто (включая админов и "царя") не должен иметь технической возможности украсть или подделать токены незаметно.

**Концепция (Immutable Ledger):**

1. **Append-Only БД + Hash Chain:**
   - Запретить `UPDATE` и `DELETE` для таблицы `token_transactions` на уровне триггеров БД.
   - Добавить колонки `prev_hash` (хэш предыдущей транзакции) и `row_hash` (хэш текущей + предыдущей).
   - Создать скрипт-валидатор для проверки целостности всей цепочки за любой период.
2. **Ежедневный Snapshot + Биткоин-якорение:**
   - Создать таблицу `audit_snapshots`.
   - Написать Scheduled Function `daily-audit.js`: раз в сутки считать общую сумму балансов (должна быть 888 800), брать `row_hash` последней транзакции и якорить этот отпечаток в Биткоине через OpenTimestamps.

   - Встроенный JS-валидатор, который в браузере проверяет хэш-цепочку (доказывает отсутствие подлога).

**Ценность:** Полная прозрачность. Аудитор может проверить любую транзакцию за год и убедиться, что она не была изменена (через Биткоин). Защита от "тихой кражи" на уровне архитектуры.

### 2026-11-15 (Принципы Zero-Trust Токеномики  по совету Джимми)
**Главное:** Переход от "доверия к админу" к "математической верификации". Система не должна иметь скрытых лазеек.

**Ключевые принципы для реализации:**
1. **Hard Cap (Математический потолок):** 8 888 токенов (888 800 микротокенов). Ни одна транзакция не может нарушить эту сумму.
2. **Append-Only Ledger (Неизменяемый журнал):** Балансы  это не просто цифры в таблице, а сумма всех транзакций. Любая попытка изменить историю (UPDATE/DELETE) ломает хэш-цепочку. Триггеры БД запрещают редактирование.
3. **No God Mode (Отсутствие ручного управления):** Казна не раздает токены вручную. Эмиссия детерминирована (привязана к Proof-of-Contribution  например, созданию сертификата). Никто не может заморозить или перевести чужие токены.
4. **Timelock (Задержка обновлений):** Любое изменение правил (например, стоимость сертификата или формула комиссии) вступает в силу только через 48 часов после публикации. Это дает время аудиторам проверить код.
5. **Verify, Don't Trust (Публичная верификация):** Любой пользователь может скачать лог транзакций и локально проверить целостность (страница `audit.html` + Биткоин-якорение).

**Важно (предупреждение Джимми):** Не допустить "абсолютной жесткости". На старте могут быть математические ошибки. Нужен механизм обновления протокола (с прозрачным Timelock), чтобы исправить баги без слома системы.
