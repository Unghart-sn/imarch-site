## Блок 1. AI RAG-Assistant (Gemini + Vectorize 768)

### 1.1. Vector Storage & Indexing Pipeline

- **Индекс:** создать векторный индекс Cloudflare Vectorize:
  ```bash
  wrangler vectorize create imarch-docs-index --dimensions=768 --metric=cosine
  ```
- **Провайдер эмбеддингов:** строго Google `text-embedding-004` (размерность **768**). Размерность фиксирована навсегда: Cloudflare Vectorize не позволяет изменить конфигурацию индекса после создания.
- **Скрипт индексации (`build_knowledge_base.py`):**

  - Чанкинг: 400–600 токенов с перекрытием (overlap) 100 токенов.
  - Метаданные чанка: `title`, `url`, `heading`, `text`.
  - Переводит чанки в векторы (768d) и загружает batch-запросами в Vectorize.

### 1.2. Cloudflare Worker (Backend Logic)

**`wrangler.toml`:**
```toml

main = "src/index.ts"
compatibility_date = "2026-11-01"

[[vectorize]]
binding = "VECTORIZE_INDEX"
index_name = "imarch-docs-index"

[[ratelimits]]
name = "RAG_RATE_LIMITER"
namespace_id = "1001"
  [ratelimits.simple]
  limit = 10
  period = 60

[vars]
LLM_PROVIDER = "google-ai-studio"   # или "openai"
LLM_MODEL = "gemini-2.5-flash"      # или "gpt-4o-mini"

# Секреты (wrangler secret put):
# GEMINI_API_KEY
# OPENAI_API_KEY (добавить позже)
# AI_GATEWAY_URL (добавить позже)
```

**Логика `src/index.ts`:**
- **Rate Limiting:** проверка по составному ключу `visitor_id` (генерируется фронтендом, хранится в `localStorage`) + `cf-connecting-ip` как fallback. Cloudflare не рекомендует IP как единственный ключ (много пользователей за одним IP).
- **Vector Search:** векторизация входящего `query` → поиск top-3 близких чанков в Vectorize (`returnMetadata: "all"`).
- **System Prompt:**
  > «Ты — главный системный архитектор и официальный ассистент проекта. Отвечай строго по предоставленному контексту. Не фантазируй и не используй внешние знания. Если ответа нет — прямо скажи об этом. Контекст: {context}»
- **Streaming:** возврат ответа в формате Server-Sent Events (SSE) / `ReadableStream`.

### 1.3. LLM-провайдер: переключаемый

- **Эмбеддинги фиксированы на Gemini `text-embedding-004`, dims = 768.** Индекс Vectorize создаётся один раз под 768 и **не пересоздаётся** при смене LLM.
- **LLM переключается через env** (`LLM_PROVIDER`, `LLM_MODEL`). Реализация — через Cloudflare AI Gateway (OpenAI-совместимый эндпоинт).
- **Почему OpenAI для ответов:** ChatGPT структурирует ответы (списки, шаги, иерархия) лучше, чем Gemini. Для справочного виджета структура важнее сырой точности.
- **Что НЕ меняется при смене LLM:** индекс Vectorize (768), пайплайн индексации, фронтенд-виджет, SSE-стриминг.
- **Что меняется:** только URL и тело запроса в Worker'е. Оба провайдера поддерживают SSE.
- **Полная миграция на OpenAI-эмбеддинги** (`text-embedding-3-small`, 1536 dims) — отдельная задача с переиндексацией всего корпуса. Не входит в текущий этап.

### 1.4. Frontend Widget (`ai-widget.js` & `ai-widget.css`)

## Блок 2. SSO & Cross-Domain Navigation (Auth-Widget)

### 2.1. Cookie & Auth Proxy Architecture

- **Провайдер Auth:** Supabase (JWT, подпись RS256).
- **Cross-Domain Session:** при авторизации на поддомене приложения (`app.imarch.ltd`) сессионный токен выставляется на основной домен: `Domain=.imarch.ltd` (ведущая точка). Флаги: `HttpOnly`, `Secure`, `SameSite=Lax`. Cookie выставляет **только** Auth-домен; остальные поддомены — только читают.
- **Worker Edge Validation:** Cloudflare Worker валидирует JWT-токен на Edge **через JWKS Supabase** (`https://<ref>.supabase.co/auth/v1/.well-known/jwks.json`, алгоритм RS256, библиотека `jose`). Без обращения к тяжёлым БД. Ключи кешируются в памяти Worker'а.
- **Ограничение безопасности (RFC 6265):** cookie не дают гарантий целостности для соседних поддоменов. Митигация: HSTS на top-level domain + cookie выставляет только Auth-домен.

### 2.2. Frontend Module (`auth-nav.js`)

Асинхронный JS-скрипт для шапки статического сайта. **Не блокирует рендеринг.**

1. **Мгновенный рендер (гость):** сразу рисует кнопку «Войти» (`app.imarch.ltd/login?redirect_to={current_url}`).
2. **Фоновая проверка сессии:** параллельно запрашивает `/api/v1/auth/me` у Auth-Worker.
3. **Состояние «Залогинен»:**
   - Заменяет «Войти» на активный «глазок» / аватар / индикатор сессии.
   - Выпадающее меню: имя, роль, кнопка **«В Личный Кабинет»** (`app.imarch.ltd/dashboard`).
   - Если вход был из приложения (`?from=app`) — плавающая кнопка `← Назад в аккаунт`. Показывается **только** при валидной сессии **и** наличии `?from=app`.
4. **Состояние «Гость»:** кнопка «Войти» (см. п.1).

### 2.3. Auth-Worker (`/api/v1/auth/me`)

1. Принимает запрос с cookie (сессионный токен Supabase).
2. Валидирует JWT через JWKS Supabase (RS256, `jose`).
3. Если валиден: `{ authenticated: true, user: { id, email, role, avatar } }` + заголовок `X-User-Authenticated: true`.
4. Если не валиден: `{ authenticated: false }` + `X-User-Authenticated: false`.
5. **БД не используется** для валидации токена — только проверка подписи через JWKS.

## Блок 3. PWA / TWA Mobile Readiness

- Веб-кабинет (`app.imarch.ltd`) должен содержать корректный `manifest.json` и базовый `service-worker.js`.
- Все авторизационные механизмы и куки должны работать внутри оверлейного контейнера (Trusted Web Activity) без сброса сессий.
- **Стратегия кеширования `service-worker.js`:**
  - Статика (JS/CSS/шрифты) — `cache-first`.
  - `/api/v1/auth/me` и страницы логина — `network-first` или `no-store`. **Не кешировать**, иначе TWA после логина покажет закешированную «гостевую» версию.
- Код готов к упаковке в TWA-контейнер (`Bubblewrap`) для релиза в Google Play.

# Дополнение к ТЗ: Design Consistency (витрина vs продукт)

**Дата:** 2026-11-09
**Статус:** к реализации
**Относится к:** RAG-виджет, SSO-модуль, лендинг, кабинет `/app/`

---

## Цель

Обеспечить визуальное единство лендинга (витрина) и личного кабинета (продукт) **без полного редизайна** и без унификации компоновки. Пользователь при переходе между поверхностями должен чувствовать «одна компания, разные разделы», а не «два разных сайта».

---

## 1. Принцип: marketing site ≠ product UI

Лендинг и кабинет решают разные задачи, и их компоновка **должна оставаться разной**:

| Поверхность | Роль | Компоновка | Плотность |
|---|---|---|---|
| Лендинг (`imarch.ltd`) | Витрина: зацепить, объяснить, продать | Верхнее меню, якоря, крупные блоки | Воздух, крупные отступы |
| Кабинет (`app.imarch.ltd/app/`) | Инструмент: работать, управлять | Боковая панель, карточки, таблицы | Компактно, плотно |

**Не унифицировать:** компоновку, размеры заголовков, плотность, тип навигации. Это разделение ролей, а не баг.

---

## 2. Что должно совпадать (обязательно)

Чтобы не было «двух миров», следующие вещи **должны быть общими** для лендинга и кабинета:

1. **Шрифтовая пара.** Одна гарнитура для заголовков, одна — для тела. Размеры могут отличаться, семейство — нет.
2. **Акцентный цвет.** Основной акцент (кнопки, ссылки, активные состояния) — один и тот же. Фон может отличаться, акцент — нет.
3. **Форма кнопок и скругления.** Радиус скругления (`--radius-*`) и стиль кнопок (заливка/обводка/тень) — единые.
4. **Стиль иконок.** Одна толщина линии, один стиль заливки (линейные vs заполненные) — на обеих поверхностях.
5. **Тень карточек.** `--shadow-card` — один и тот же (или два уровня: `sm` для кабинета, `md` для лендинга, но из одной шкалы).

---

## 3. Что можно (и нужно) делать разным

- **Плотность.** Лендинг — воздух, крупные H1, большие отступы. Кабинет — компактные карточки, таблицы.
- **Навигация.** Лендинг — верхнее меню с якорями. Кабинет — боковая панель.
- **Размеры типографики.** Лендинг — крупные H1, кабинет — мелкие, но из той же гарнитуры.
- **Градиенты/подложки.** Лендинг может позволить более смелые градиенты/фоны. Кабинет — строже, нейтральнее.
- **Иллюстрации.** Лендинг — крупные абстрактные иллюстрации. Кабинет — линейные иконки.

## Уточнённое ТЗ: R&D-модули (Voice, Motion, Memory, REA)

### 1. Локальная озвучка (Voice Studio / TTS)

**Проблема в исходном ТЗ:** «клонирование голоса» звучит как кнопка. На деле нужен референс (3–20 секунд чистой речи) и юридическая чистота.

**Конкретный инструмент:** `voicebox` (Tauri/Rust, не Electron, работает локально, Docker есть). Пять движков, 23 языка, клонирование с нескольких секунд, REST API для интеграции в `build_full_video.py` .

**Альтернатива для простого TTS без клонирования:** `supertonic-server` — OpenAI-совместимый эндпоинт (`/v1/audio/speech`), работает на CPU/CoreML/CUDA, ~99M параметров, 31 язык, 10 голосов. Первый байт ~450–650 мс после прогрева . Если клонирование не нужно — это самый лёгкий путь.

**Что зафиксировать в ТЗ:**
- Инструмент: `voicebox` (Docker: `docker compose up`) или `supertonic-server`.
- Клонирование: **только свой голос или с письменного согласия**. Референс — 3–20 секунд, без фонового шума.
- Интеграция: REST API (`voicebox`) или OpenAI-совместимый `/v1/audio/speech` (`supertonic-server`) → вызов из `build_full_video.py`.

### 2. HyperFrames (программный моушн-дизайн)

**Проблема в исходном ТЗ:** «генерация промо-роликов по JSON/скриптам» — неточно. HyperFrames рендерит **HTML-композиции**, которые пишет агент, а не JSON.

**Что это на самом деле:** open-source (Apache 2.0) движок от HeyGen. Видео — это HTML-файл с `data-*` атрибутами для тайминга. Анимация — GSAP, CSS, Lottie, Three.js, Anime.js, WAAPI. Рендер: headless Chrome + FFmpeg, детерминированный (один и тот же вход → один и тот же выход) . CLI: `npx hyperframes render`.

**Ключевая фича для Imarch:** агент (Claude Code, Codex) уже умеет писать HTML. HyperFrames даёт ему **skill-файлы** и **каталог готовых блоков** (`npx hyperframes add flash-through-white`), чтобы он собирал промо-ролик по описанию, а не гадал .

**Что зафиксировать в ТЗ:**
- Вход: описание сценария или URL сайта (для съёмки реальных экранов).
- Агент пишет `index.html` с `data-start`, `data-duration`, `data-track-index`.
- Рендер: `npx hyperframes render` → MP4.
- Для Verdictum/Chronicle OS: использовать `/product-launch-video` workflow (снимает сайт по URL, строит ролик) .

### 3. Персистентная память агентов («Hide»)

**Проблема в исходном ТЗ:** «Hide» — не публичный инструмент. Нужно конкретное имя.

**Конкретный инструмент:** `agentmemory` (24k+ звёзд, Apache-2.0, TypeScript/MCP). Работает с Claude Code, Codex, Cursor, Gemini CLI и любым агентом, говорящим на MCP или REST. Установка: `npx -y @agentmemory/agentmemory@latest` . Память живёт в `%APPDATA%\agentmemory` на Windows, переживает перезапуски. Захватывает сессии, сжимает в поисковую память, инжектит контекст при старте следующей сессии .

**Альтернатива:** `Hippocampus-MCP` (многоуровневая память L0–L3: raw → facts → summaries → profile). Если нужна более сложная иерархия — но для старта `agentmemory` проще.

**Что зафиксировать в ТЗ:**
- Инструмент: `agentmemory`.
- Установка: `npx -y @agentmemory/agentmemory@latest`.
- Интеграция: MCP-сервер, подключается к Claude Code / Codex / Cursor.
- Данные: локально, без облака.

### 4. Агентный реверс-инжиниринг («Франкенштейн»)

**Проблема в исходном ТЗ:** «скармливание исходников» — REA работает **не с исходниками**, а с бинарниками, упакованными приложениями и веб-структурами. Если исходники есть — REA не нужен.

**Что это на самом деле:** REA — локальный MCP-сервер, который подключает агента к Ghidra, Hopper, IDA (для нативных бинарников), Node.js (для JavaScript/Electron), Chrome (для сайтов), JADX (для APK), Binwalk (для firmware). # Архитектурный манифест: Суверенная Serverless & Media-контент фабрика

Никакой магии, только чистый Serverless на краю (Edge) и локальный пайплайн на десктопе. Вся система собирается в единый замкнутый контур с нулевыми постоянными издержками.

```text
[ Исходный контент (Markdown / Спецификации / Посты) ]
                       │
       ┌───────────────┴───────────────┐
       ▼                               ▼
[ 1. Web & Edge Layer ]        [ 2. Media Foundry Layer ]
(Cloudflare Stack)             (Local Python / FFmpeg Pipeline)
  ├─ Vectorize (768-dim RAG)     ├─ Supertonic TTS (Локальный голос)
  ├─ Auth Proxy (Cross-SSO)      ├─ FFmpeg (Авто-микширование музона)
  └─ PWA/TWA (Google Play)       └─ HyperFrames (Программный моушн)
                       │                       │
       └───────────────┬───────────────┘
                       ▼
         [ 100% Автономный результат: ]
  Сайт с ИИ-ассистентом + Мобильное приложение 
  + Регулярный поток готовых видео и подкастов

```

---

### Контур 1: Веб-инфраструктура и Интеллект (Cloudflare Edge)

* **Назначение:** Лицом наружу, доступность 99.99%, мгновенный отклик для клиентов и пользователей.
* **Что работает:**
* **RAG AI-Assistant:** Чанкинг документов, векторный поиск по 768-мерному индексу (`text-embedding-004`) + Cloudflare Vectorize + Google Gemini Flash. Защита лимитов по `visitor_id + IP`.
* **Cross-Domain SSO:** Единая кука (`Domain=.yourdomain.com`), Auth-Worker на Edge, плавающий «глазок» сессии и мгновенный возврат в личный кабинет.
* **Mobile Readiness:** Упаковка веб-интерфейса в PWA/TWA через `Bubblewrap` для прямой публикации в Google Play без модерационных задержек.



### Контур 2: Локальная Медиа-Фабрика (Десктоп / Python Core)

* **Назначение:** Фабрика контента для канала `visrealitatis`, соцсетей и промо-материалов.
* **Что работает:**
* **Голос (`supertonic-server`):** Локальный микро-сервер на CPU, выдающий чистый аудиопоток за 500 мс по OpenAI-совместимому API.
* **Сведение звука (`ffmpeg`):** Автоматическое наложение фоновой музыки с эффектом *ducking* (приглушение под речь) и плавным затуханием (fade-out).
* **Визуал (`HyperFrames`):** Программный рендеринг кинематографичных UI-анимаций и схем по скриптам.
* **Пайплайн (`build_full_video.py`):** Один запуск скрипта превращает свежий Markdown-файл в готовый vertical MP4 с озвучкой, сабтитрами и саундтреком.



### Контур 3: Память и Разработка (DevOps & R&D)

* **Назначение:** Ускорение работы кодинг-агентов и суверенная разработка.
* **Что работает:**
* **Персистентная память (`Hide` в Docker):** Фиксация архитектурных правил, контекста и решений между сессиями ИИ-агентов.
* **Агентный реверс-инжиниринг:** Инструментарий для разбора чужих библиотек и форматов на атомы силами локальных CLI-агентов.



---

### Философия подхода

1. **Суверенитет данных:** Никакие чужие облака не читают твои документы, не хранят ключи и не диктуют лимиты.
2. **Себестоимость операций:** Инфраструктура сайта стоит сущие центы на Serverless, а генерация медиаконтента стоит ровно 0$ (работает на железе разработчика).
3. **Масштабируемость в B2B:** Любой из этих модулей (будь то RAG-виджет, SSO-авторизация или медиа-пайплайн) упаковывается в коробочное решение и продается клиентам как премиальный архитектурный консалтинг от LTD.

## Техническое задание: Разработка SaaS-страницы договорных документов и юридических условий

### 1. Назначение и общая концепция

Создание единого, визуально чистого и юридически безупречного интерфейса для отображения публичной оферты, пользовательского соглашения (Terms of Service), политики конфиденциальности и сопутствующих регламентов платформы IMARCH LTD. Страница должна гармонично вписываться в общую дизайн-систему (типографика, строгая сетка, минимализм) и обеспечивать жесткую фиксацию версий документов.

---

### 2. Требования к фронтенду (для Линя)

* **Макет и верстка:**
* Двухколоночная структура: слева — фиксированное оглавление (Table of Contents) с плавным скроллом и подсветкой активного раздела; справа — основное текстовое полотно.
* Типографика: строго контролируемая ширина строки (readability limit, ~65–75 символов), четкая иерархия заголовков, контрастные отступы для списков и таблиц (в стиле качественной программной документации).
* Адаптивность: корректное складывание в одноколоночный вид на мобильных устройствах с выпадающим меню навигации по разделам.


* **Функциональные элементы на странице:**
* **Селектор версий:** выпадающий список или переключатель истории редакций документов (с указанием дат вступления в силу). При смене версии контент обновляется динамически или через мягкую перезагрузку.
* **Кнопка экспорта/печати:** бымая генерация чистого для печати или сохранения в PDF/Markdown вида (без интерфейсных обвесов).
* **Прямые якоря (Anchors):** возможность скопировать ссылку на конкретный пункт договора (например, `/terms/#clause-4-2`).



---

### 3. Бэкенд, версионирование и логирование (Zero-Trust подход)

* **Хранение документов:**
* Исходники текстов хранятся в виде версионированных Markdown-файлов в репозитории (или базе данных с контролем целостности).
* Каждая редакция документа получает уникальный хэш (например, SHA-256), гарантирующий неизменность текста с момента публикации.


* **Фиксация согласия (Audit Trail):**
* При регистрации или чекауте пользователь должен явно подтвердить согласие с актуальной редакцией (активный чекбокс с фиксацией версии документа и временной метки).
* В базе данных сохраняется связка: `User ID` + `Document Version Hash` + `Timestamp` + `IP/Session Metadata` для исключения любых юридических разногласий в будущем.



---

### 4. Интеграция в пользовательский путь (UX Flow)

* **Онбординг / Регистрация:** Блокировка завершения регистрации до момента проставления отметки об ознакомлении с актуальной офертой.
* **Ссылки в системе:** Постоянное присутствие ссылок на актуальные редакции в футере сайта, в личном кабинете пользователя, а также в системных транзакционных письмах.
